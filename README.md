# Claude Auto Flow

Claude Code用の自律ワークフロー・オーケストレータースキルです。「検討 → 計画 → 実装 → 独立レビュー → セキュリティチェック → マージ判定」の一連の流れを、ユーザーへの確認なしに最後まで自動進行させ、全ゲートに合格した場合のみ main へ自動マージします。

## 概要

`auto-flow` は以下のパイプラインを完全自律で実行するオーケストレータースキルです。

```
[0]起動 → [1]調査(任意) → [2]検討 → [3]計画 → [4]実装 → [5]レビュー ⇄ [5']自動修正(最大2周)
          Haiku          Opus⇄Fable Sonnet⇄Opus Sonnet  Sonnet⇄Opus   Sonnet
 → [6]セキュリティチェック&ブランチpush(Haiku) → [7]マージ判定ゲート → [8]完了報告
```

- 作業はすべて作業ブランチ `auto-flow/<slug>` 上で行い、main には [7] のゲートに全合格した場合のみマージする
- 各フェーズはサブエージェントとして起動され、成果物は `.auto-flow/<実行ID>/` に保存される（中断しても再開可能）
- [5] のレビューは実装時の会話を持たない新規コンテキストで行い、軽微な指摘は自動修正、重大な指摘は停止する
- 小規模な課題（1文で説明でき、変更3ファイル以内）は検討・計画を省略する短縮ルートで進む
- 各スキルに組み込まれた承認ゲート（「実装してください」待ち、プッシュ前確認など）は、本フロー内では自動承認として扱われる
- 起動は、ユーザー自身の発話に含まれる起動語または `/auto-flow` で行う。起動語の発話ごとに短命の**起動認可**を発行し、認可がない実行は main へマージしない（誤起動対策。後述）

## 依存関係

このスキルは単体では動作しません。以下のリポジトリで公開されている5つのスキルを事前に `~/.claude/skills/` に配置しておく必要があります。

**[rapyutapazoo-design/claude-skills](https://github.com/rapyutapazoo-design/claude-skills)**

- `consultant-mode` — 検討フェーズ
- `plan-creator` — 計画フェーズ
- `researcher` — 調査フェーズ（任意）
- `safe-push` — セキュリティチェック&ブランチpushフェーズ
- `git-workflow` — 単体利用のみ（auto-flow内では使用しない）

動作環境:

- Python 3.9 以上（標準ライブラリのみ使用）
- git 2.31 以上（Git ガードの reference-transaction フックは 2.28 以上、G7 の `git merge-tree --write-tree` は 2.38 以上）
- `gh` CLI（任意。あれば PR 経由でマージ、無ければローカルで ff マージ）

## インストール手順

`SKILL.md` に加えて `hooks/` ディレクトリも配置してください（Git ガードと起動認可の本体）。

```bash
mkdir -p ~/.claude/skills/auto-flow
cp -R SKILL.md hooks ~/.claude/skills/auto-flow/
```

さらに、起動認可の発行フックを `~/.claude/settings.json` の `hooks` に登録します（既存の `hooks` がある場合は各配列に追加してください）。

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "f=\"$HOME/.claude/skills/auto-flow/hooks/prompt_token.py\"; [ -f \"$f\" ] || exit 0; command -v python3 >/dev/null 2>&1 || exit 0; python3 \"$f\" >/dev/null 2>&1; exit 0",
            "timeout": 10
          }
        ]
      }
    ],
    "UserPromptExpansion": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "f=\"$HOME/.claude/skills/auto-flow/hooks/prompt_token.py\"; [ -f \"$f\" ] || exit 0; command -v python3 >/dev/null 2>&1 || exit 0; python3 \"$f\" >/dev/null 2>&1; exit 0",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

このフックを登録しなくてもスキル自体は動きますが、起動認可が発行されないため、**G8 が不合格になり、常に PR 作成で止まります**（main へは自動マージされません）。

## 使い方

次のいずれかで起動します。

- 起動語を含む発話: 「オートフロー」「auto-flow」「自律実行して（ください）」「自動で最後まで進めて」「全自動で進めて」
- スラッシュコマンド: `/auto-flow <課題>`

起動語を含んでいても、auto-flow への言及・質問・説明依頼・検討依頼・改善依頼（例:「auto-flow の改善を検討して」）では起動しません。

| オプション | 効果 |
|---|---|
| `--research` / 「調査込みで」 | 冒頭に調査（researcher）フェーズを追加 |
| `--economy` / 「節約モードで」 | 検討=Opus・計画=Sonnet に固定（コスト優先） |
| `--fable` / 「最高品質で」 | 検討=Fable 5・計画=Opus に固定（品質優先） |
| `--no-merge` / 「PRまで」「mainに入れないで」 | main へ自動マージせず PR 作成で止める |
| 「auto-flow 再開」 | `.auto-flow/` の最新の中断地点から再開（「再開」単独は不可） |

`.auto-flow/` は `.git/info/exclude` に自動で追記されるため、コミットされません。

## 起動認可（誤起動対策）

起動語は文字列一致で検出するため、「auto-flow の説明をして」のような発話でも語が含まれます。誤って自律実行が走っても main が更新されないよう、起動認可の仕組みで守ります。

1. **トークン発行**: `hooks/prompt_token.py`（`UserPromptSubmit` / `UserPromptExpansion` フック）が、**ユーザー自身の発話**に起動語が含まれるときだけ、10分有効のトークンを `~/.claude/auto-flow/tokens/<session_id>.json` に発行します。サブエージェントの入力、`<system-reminder>` などの自動ターン、ツール結果やファイル内の語は対象外です。起動語は NFKC 正規化・小文字化のうえ部分一致で判定します。
2. **認可レコード**: 起動時に `install_guards.py install --session <ID> --run-id <実行ID>` がトークンを消費し、Git 共通ディレクトリ配下の `auto-flow-auth/<auth_id>.json` に認可レコードを作ります。`state.json` の `auth_id` に記録され、再開時は旧認可を失効させて取り直します。
3. **検証**: G8 は「ガードの設置確認」に加えて「認可レコードが存在し、実行ID・時刻が整合していること」を要求します。Git フックも、認可がない実行では main への更新を拒否します。
4. **原文照合**: 起動時と再開時に、ユーザーの直近の発話に起動語が文字どおり含まれるかを確認します。含まれない場合は何も作らず終了します。

認可がない場合は停止ではなく「PR 止め」（G8 不合格）になります。フック未設定、`prompt_token.py` 不在、`session_id` 不一致の場合も常に認可なし＝PR 止めで、安全側に倒れます。

## モデル配分表（フェーズ別・動的選択）

各フェーズは、コストが最小になるモデルを割り当てたサブエージェントで実行されます。検討・計画・レビューは、課題の難易度・実装規模に応じてフェーズごとに独立してモデルを昇格させる動的選択方式です（デフォルトはトークン消費が少ない方を優先）。

| フェーズ | モデル | 昇格条件 |
|---------|--------|---------|
| 調査（任意） | Haiku | 固定 |
| 検討 | Opus（既定）／ Fable 5（難タスク時） | 5基準中2項目以上該当で Fable 5 へ昇格 |
| 計画 | Sonnet（既定）／ Opus（複雑時） | 4基準中2項目以上該当で Opus へ昇格 |
| 実装・自動修正 | Sonnet | 固定 |
| レビュー | Sonnet（既定）／ Opus | 計画が Opus に昇格した場合、または差分が 300 行超・10 ファイル超 |
| セキュリティチェック & ブランチpush | Haiku | 固定 |

**検討フェーズの昇格基準（5項目）:** ① 設計空間が広い ② 複数システム・技術の横断 ③ 要件が曖昧で前提設定が必要 ④ 新規アーキテクチャ設計 ⑤ 相反するトレードオフが3つ以上。Fable 5 が利用不可の環境では Opus に自動フォールバックします。

**計画フェーズの昇格基準（4項目）:** ① 実装ステップ見込みが多い（目安: 対象ファイル5以上またはステップ8以上）② コンポーネント間の依存順序が複雑 ③ 破壊的変更・データ移行を含む ④ 採用案に未確定の技術判断が残っている。

**リトライ:** フェーズが失敗した場合、1回目は同じモデルで、2回目は1段上のモデル（Haiku→Sonnet→Opus→Fable 5）で再実行し、それでも失敗したら停止します。

選択されたモデルと判定根拠は開始宣言に、実際に使用したモデルは完了報告のモデル列に記録されます。

> **設計意図:** 検討は方向を決める回復不能な工程のため品質の床を Opus に保ちつつ難タスク時のみ Fable 5 へ昇格、計画は構造化作業で実装エージェントの裁量により部分回復が可能なため Sonnet まで下げられる、という非対称2択です。

## レビューの重要度基準

| 区分 | 例 | 扱い |
|---|---|---|
| 軽微 | 命名・可読性、エッジケースのテスト不足、変更行内で完結する小バグ、lint 違反、ログ/コメント | 自動修正 → 再レビュー（最大2周） |
| 重大 | セキュリティ、データ損失・破壊的変更、要件/計画との乖離、公開API互換性破壊、設計変更が必要なもの | 停止（作業ブランチを push して報告） |

判定に迷うものは重大として扱います。

## マージ判定ゲート（G1〜G8）

すべて合格した場合のみ main へ自動マージし、1つでも不合格なら PR を作成して停止します。

| ID | 条件 |
|---|---|
| G1 | マージ抑止の指示がない（`--no-merge` 等） |
| G2 | テスト・ビルドをオーケストレーター自身が実行し、終了コード 0（自己申告は不可。テストが無い場合は不合格） |
| G3 | レビューの重大指摘 0 件、軽微な指摘もすべて解消済み |
| G4 | safe-push の結果が 🟢 のみ（🟡 は不合格） |
| G5 | 重要パス（DB マイグレーション、認証、CI/CD 設定、インフラ定義、依存のメジャー更新など）に触れていない |
| G6 | 変更ファイル 15 以内かつ削除ファイルなし |
| G7 | ベースブランチがコンフリクトなく取り込める |
| G8 | Git ガードが設置済みで実際に機能している（プローブで確認）、かつ起動認可が有効（認可なしは PR 止め） |

## 停止条件

以下の場合のみ停止します。それ以外は最後まで自律的に完了します。

- Git リポジトリがない、または未コミットの変更がある（起動時）
- セキュリティチェックで 🔴（シークレット漏洩・除外ファイル混入）を検出（push しない）
- レビューで重大な指摘（作業ブランチを push して報告）
- 自動修正が2周で収束しない
- リトライ上限を超えた
- マージ判定ゲートが不合格（PR を作成して正常終了。ガード設置失敗や起動認可なしもここに含まれる）

## Git ガード（main の保護）

main への自動マージを安全に行うため、2層のガードで「ゲート合格前に main を更新できない」ことを仕組みで保証します。

| 層 | 仕組み | 守るもの |
|---|---|---|
| 層1（主） | Git ネイティブフック（`reference-transaction` / `pre-push` / `pre-commit`） | ゲート合格前の main/master/ベースブランチの更新・push（コマンドの書き方に関係なく Git 本体が検査）、機密ファイルのコミット |
| 層2（補助） | Claude Code の PreToolUse フック（`hooks/af_guard.py`） | `gh pr merge`（サーバー側マージ）、`--no-verify` や `core.hooksPath` などのガード迂回、フック・リモート設定の改変 |

- 層1は auto-flow の初回起動時に対象リポジトリへ自動で設置されます（git 2.54 等の設定ベースのフックに対応していれば `.git/config` に登録、非対応ならシムを `.git/hooks/` に設置し、既存フックは退避して連鎖実行）。
- **auto-flow が実行中でないときは何もしません。** 設置したままでも通常の git 操作には影響しません（空コミット20回で約1秒のオーバーヘッド）。
- ゲート合格後に通すのは、作業ブランチの先端そのもの、または「ベースと作業ブランチ先端をちょうど2つの親に持つ」マージコミット、およびリモートの実際の先端と一致する ff 同期だけです。

### ガードの撤去

```bash
python3 ~/.claude/skills/auto-flow/hooks/install_guards.py uninstall --repo <リポジトリのパス>
```

**スキルを移動・削除する前に、設置済みの全リポジトリで uninstall してください。**（ガード本体が見つからない場合フックは素通りになるため git 操作は止まりませんが、保護も効かなくなります）

### 既知の限界

- 目的は事故防止です。Claude が Write/Edit ツールで `.git/config` や `.git/hooks` を直接書き換えるような意図的な迂回は防げません。
- `--no-verify` 等による迂回は層2の文字列判定でのみ防ぐため、best-effort です。
- `gh pr merge` によるサーバー側マージは層2とゲートのみで守ります。
- スキルに登録した層2のフックがサブエージェント内で発火するかは未確認です（main の操作はオーケストレーター本人のみが行う設計で補っています）。
- 起動トークンは起動語の**文字列一致**で発行されます。起動語を含む言及・検討依頼の直後 10 分以内に Claude が誤起動すると認可され得ます（起動時の原文照合と description が防御）。
- Claude 自身によるトークン・認可レコードの偽造（直接書き込みや `prompt_token.py` への偽入力）は想定外です。実行中の書き込みのみ、層2で best-effort に拒否します。
- 自動ターン（タスク通知など）の判別は、先頭タグ（`<task-notification` / `<system-reminder` / `<scheduled-task`）での除外のみです。

## テスト

```bash
python3 -m unittest discover -s hooks/tests -v
```

一時 git リポジトリ上で実際に git コマンドを実行し、main の更新がブロック／許可されることを検証します（約90秒）。ユーザーのグローバル git 設定からは隔離して実行されます。

## 変更履歴

- **v4** — 起動認可（`prompt_token.py` による起動トークンと認可レコード）を追加し、G8 に認可検証を組み込み。起動方式を「起動語＋`/auto-flow`」に戻し、誤起動は原文照合と認可で防ぐ方式に変更
- **v3** — 独立レビューと自動修正、マージ判定ゲート（G1〜G8）による main への自動マージ、Git ガード、成果物の保存と再開、短縮ルート、リトライ時のモデル昇格を追加（起動は `/auto-flow` のみ）
- **v2** — フェーズ別の動的モデル選択（検討 Opus⇄Fable 5、計画 Sonnet⇄Opus）と `--economy` / `--fable` オーバーライドを導入
